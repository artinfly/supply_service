# supply_service

Django-сервис отчётности отдела снабжения: договоры, заявки на платёж и выгрузки
в Excel. Данные приходят выгрузками из внешних систем, загружаются через веб или
командой, дальше показываются на дашбордах и в реестрах.

## Страницы

| Адрес | Что показывает | Кому |
|---|---|---|
| `/reports/` | обзор со ссылками на разделы | всем |
| `/reports/dashboard/` | договорная работа | superuser |
| `/reports/znp/` | заявки на платёж (ФЗД) | superuser |
| `/reports/znp-sap/` | заявки на платёж (SAP) | superuser |
| `/reports/all-contracts/` | реестр договоров | всем |
| `/reports/znp-list/` | реестр ЗнП (ФЗД) | всем |
| `/reports/znp-sap-list/` | реестр ЗнП (SAP) | всем |
| `/reports/kdr/<год>/` | заключение договоров по ИГК | всем |
| `/reports/igk-concluded/<год>/` и рядом | ИГК по состояниям | всем |
| `/reports/history-*/` | история статусов, плана, факта | всем |
| `/reports/contract-dupes/` | дубликаты | всем |
| `/reports/export/` | отчёты в Excel | всем |
| `/reports/upload/` | загрузка файлов | operator, superuser |

Меню собрано по назначению: сначала «Сводки» (дашборды), сразу за ними
«Реестры», дальше КДР, ИГК, история и служебные страницы.

В реестрах одинаковые фильтры: поиск, ИГК, ЦФО, год, состояние. Поиск — одно
поле сразу на контрагента и номер договора, по части строки.

Внизу каждого дашборда, под таблицей по ЦФО, график: горизонтальные стопки по
ЦФО, отсортированные по сумме. Договорная работа — сегменты по давности срока
подписания, ЗнП (ФЗД) — по стадиям заявки, ЗнП (SAP) — по этапам согласования.
Числа те же, что в таблице выше; график добавляет сравнение между ЦФО.

Цвет карточек и сегментов читается как движение по этапам: красный (стоит) →
оранжевый (в работе) → синий (почти) → зелёный (готово). Четыре оттенка
проверены на различимость, в том числе при дальтонизме.

Роли задаются в `/admin/`: Пользователи → выбрать → Группы. Группы `viewer` и
`operator` создаёт `python manage.py setup_groups`. Разница: `operator` может
загружать файлы.

## Таблицы базы

| Таблица | Что хранит |
|---|---|
| `igk_stat_data` | позиции договоров: одна строка = один этап и один тип платежа |
| `znp_data` | заявки на платёж (ФЗД), привязаны к позиции договора |
| `znp_data_sap` | заявки на платёж (SAP), самостоятельные записи |
| `staging_excel`, `staging_znp_excel`, `staging_znp_sap_excel` | сырые строки Excel до разбора |
| `contracts_history` | изменения статуса, плана и факта между загрузками |
| `contract_counts_snapshot` | снимки числа заключённых договоров для дельты в КДР |
| `nsi_igk`, `nsi_cfo` | справочники, заполняются сами при загрузке |

### Связь ЗнП с договорами

`znp_data.parent_id` ссылается на `igk_stat_data.pp_id`, но **без ограничения
внешнего ключа**. Причина: при каждой загрузке договоров `igk_stat_data`
очищается и заполняется заново, а номера `pp_id` выдаются с нуля. Обычный
внешний ключ снёс бы все заявки каскадом.

Связь восстанавливается по `crc32_hash` — хешу от ИГК, контрагента, договора и
этапа. Этим занимается `services/linking.py::relink_znp_parents()`, его вызывает
разбор договоров последним шагом. Без этого вызова заявки остаются с номерами от
прошлой раскладки и молча оказываются привязаны к чужим договорам.

Поле `is_deleted` в `igk_stat_data` не заполняется: источник присылает полные
дубли строк без уникального идентификатора, отследить удаление нечем.

## Запуск

```bash
python -m venv .venv
.venv\Scripts\activate
pip install --no-index --find-links=wheels -r requirements.txt
```

Если базы ещё нет:

```sql
CREATE ROLE root WITH LOGIN SUPERUSER PASSWORD 'root';
CREATE DATABASE supply_service_test OWNER root;
\c supply_service_test
CREATE EXTENSION IF NOT EXISTS pgcrypto;
```

```bash
python manage.py migrate
python manage.py setup_groups
python manage.py createsuperuser
python manage.py runserver
```

Открыть `http://127.0.0.1:8000`.

`settings.py` настроен на домашнюю базу: `supply_service_test` / `root` / `root`
/ `localhost`. На работе лежит свой вариант этого файла — отличается адресом
базы.

Расширение `pgcrypto` обязательно: на нём построены история изменений и поиск
дубликатов.

При `DEBUG = False` обязателен `python manage.py collectstatic` — статика
отдаётся через WhiteNoise с манифестом, без него страницы упадут.

## Миграции

Шесть:

1. `0001_initial` — создаёт все таблицы
2. `0002_performance_indexes_and_snapshot_key` — индексы и уникальный ключ снимков
3. `0003_sap_indexes` — индексы по ЦФО и ИГК для заявок SAP
4. `0004_znp_status` — поле статуса заявки ЗнП
5. `0005_contract_sum`, `0006_staging_contract_sum` — сумма договора и её история

Модель в `models.py` описывает, как должно быть; миграция — записанный шаг, как
к этому прийти. `makemigrations` сравнивает модель с последней миграцией и пишет
разницу, `migrate` применяет её и отмечает в служебной таблице
`django_migrations`.

Проверить, что модель и миграции сходятся:

```bash
python manage.py makemigrations --check --dry-run
```

## Загрузка данных

Через интерфейс: «Загрузка данных» → выбрать файл и тип → загрузить.

Через командную строку:

```bash
python manage.py load_contracts файл.xlsx
python manage.py load_znp файл.xlsx
python manage.py load_znp_sap файл.xlsx
```

Каждая команда делает два шага одной транзакцией: кладёт сырые строки в
`staging_*`, затем разбирает их и переносит в рабочие таблицы. Если второй шаг
упадёт, первый откатится и данные останутся прежними.

Все колонки из списков ниже обязательны: нет хотя бы одной — загрузка
прерывается с сообщением, какой именно не хватает, база не меняется.

Повторная загрузка договоров сравнивается с предыдущей: изменения статуса, плана
и факта попадают в «Историю изменений». По ЗнП истории нет, хранится только
текущий снимок.

Типы файлов перечислены двумя словарями в начале `views/pages.py`. Новый тип —
пара «ключ-значение» в оба словаря.

## Формат файлов Excel

### Договоры

Заголовки в первой строке, порядок колонок не важен:

```text
ИГК | Контрагент | ЦФО | Договор | Состояние | Тип платежа | Предмет | Заказ |
ПЛАН | ФАКТ | Тол | Этап графика | ДатаПланПодп | СУММА договора | ГодИГК
```

- **ГодИГК** — четырёхзначный год, по нему работает переключатель года.
- **ДатаПланПодп** — плановая дата подписания в виде `ДД.ММ.ГГГГ`, при разборе
  приводится к `ГГГГ.ММ`. По ней считается давность на графике.
- **СУММА договора** — пишется в позицию и в историю изменений; на страницах не
  выводится, нужна для процентов в истории плана.
- **Тип платежа** — `Аванс` или `Постоплата`, прочее в расчёты не попадает.
- **Состояние**: заключённые — `Исполняется`, `Возвращен на уточнение`,
  `На согласовании`, `Подписан`, `На утверждении`, `Исполнен`; незаключённые —
  `Черновик`; расторгнутые — `Расторгнут`.

### ЗнП (ФЗД)

Заголовки в первой строке:

```text
ИГК договора | ИГК заявки | Контрагент | ДокументПланирования.Номер | Этап |
Назначение платежа | Договор | Прогнозная дата оплаты | Фактическая дата оплаты |
Сумма руб планирования | Сумма руб оплаты | ТипПлатежа | Статус
```

- **ИГК договора** — ИГК позиции, к которой привязана заявка. **ИГК заявки** —
  ИГК, по которому заявка фактически оплачена, может отличаться.
- **Этап** — это «Этап графика» из файла договоров, а не статус заявки. Значение
  должно совпадать с файлом договоров, иначе хеш не сойдётся и заявка останется
  без привязки.
- **Статус** — `Утвержден` или `На утверждении`.

### ЗнП (SAP)

Заголовки в первой строке:

```text
ИГК (по договору) | Отдел-исполнитель | Наименование кредитора |
Регистрационный номер | Текст | Сумма во ВВ | Наименование Банка |
ЗнП 421 отдел (ГОЗ) - (E) | ЗнП 18 отдел (ГОЗ) - (F) |
Платеж возможен - ( ) | СП/ГП | ДокумВыравнивания
```

Берутся только строки с типом `ГОЗ` в колонке «СП/ГП».

## Как считаются заявки на платёж

Два независимых источника: **ФЗД** и **SAP**. Заявки SAP не связаны с
`igk_stat_data` — это самостоятельные записи, и статус у них считается по датам
этапов согласования.

### ФЗД

Считаются позиции заключённых договоров, а не строки `znp_data` напрямую:

- у позиции нет ни одной заявки → «Не оформлено», отдельно по авансу и
  постоплате;
- заявка со статусом `На утверждении` → «На оформлении»;
- заявка со статусом `Утвержден` → «Оформлено», дальше по типу платежа позиции.
  Счётчик считает заявки: если у позиции их несколько, каждая идёт отдельно;
- из оформленных отдельно считается «Оплачено» — заявки с заполненной
  фактической суммой.

Заявка со статусом, отличным от `Утвержден`, считается «на оформлении» — так
не теряются записи, загруженные до появления колонки статуса.

В истории плана рядом с суммами выводится их доля от суммы договора на тот же
момент: старый план от старой суммы, новый от новой.

Суммы: «не оформлено» — плановая сумма позиции, других данных нет; «оформлено» —
плановая сумма заявок; «оплачено» — фактическая сумма заявок.

Проценты на карточках: «оформлено» — доля от общего числа, «оплачено» — доля от
«оформлено» той же группы.

Условия статуса продублированы в двух местах: `ZNP_STATUS_CONDITIONS` в
`views/api.py` (фильтр реестра) и `CASE` в `queries.py::znp_list()`
(отображаемый статус). Меняя логику, править нужно оба.

### SAP

Четыре этапа по датам: на согласовании → передано в 18 отдел → подтверждено
18 отделом → оплачено. Логика живёт в `services/sap_status.py` в одном
экземпляре: выражение для запроса и функция для построчной подписи в JSON
обязаны оставаться согласованными.

## Добавление нового года

Например, 2028. Четыре места:

**1. `services/queries.py`**

```python
YEARS = [2025, 2026, 2027, 2028]
```

**2. `models.py`** — новое поле в `IgkStatData`:

```python
y28 = models.BooleanField(null=True)
```

**3. `services/normalize.py`** — добавить `y28` в распаковку `year_flags()`, в
кортеж `new_data.append(...)` и в список колонок INSERT.

**4. Миграция:**

```bash
python manage.py makemigrations reports
python manage.py migrate
```

После этого перезагрузить файл договоров. Дашборды ЗнП править не нужно — год
они берут с самой позиции договора.
