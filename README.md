# supply_service

Приложение отчётности отдела снабжения. Принимает выгрузки Excel по договорам
и заявкам на платёж, хранит их в PostgreSQL, показывает сводки и реестры,
формирует выгрузки Excel.

## Стек

Django 6, PostgreSQL, openpyxl, whitenoise. Frontend без сборки: Bootstrap и
Chart.js лежат файлами в `reports/static/vendor/`.

## Развёртывание

Требуется PostgreSQL и расширение `pgcrypto` — на нём построены SQL истории
изменений и поиск дубликатов. Миграции расширение не создают, его нужно
включить в базе один раз:

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
```

Установка зависимостей и подготовка базы:

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe manage.py migrate
.venv/Scripts/python.exe manage.py createsuperuser
.venv/Scripts/python.exe manage.py setup_groups
```

Запуск:

```bash
.venv/Scripts/python.exe manage.py runserver
```

`CREATE EXTENSION` выполняется внутри созданной базы, а не в служебной.

### Установка без интернета

В `wheels/` лежат пакеты для офлайн-установки. Вместо обычного `pip install`:

```bash
.venv/Scripts/python.exe -m pip install --no-index --find-links wheels -r requirements.txt
```

Готовую папку `.venv` переносить с другой машины нельзя — в ней записан
абсолютный путь к Python. Её создают заново на месте.

Заранее нужны Python 3.13 и PostgreSQL: колёса `psycopg2_binary` собраны под
`cp313` и на другую версию Python не встанут.

Данные переносятся дампом. Повторная загрузка исходных файлов Excel
восстанавливает договоры и заявки, но не историю: `contracts_history` и
`contract_counts_snapshot` накапливаются от загрузки к загрузке.

```bash
pg_dump -U root -d supply_service_test -F c -f supply_service.dump
pg_restore -U root -d supply_service_test supply_service.dump
```

## Настройки

Все настройки — в `supply_service/settings.py`, включая подключение к базе.
Файл входит в репозиторий, поэтому значения в нём одинаковы на всех установках.

Ответы сжимаются `GZipMiddleware`: реестры отдают десятки тысяч строк, и без
сжатия это мегабайты на запрос.

Для боевой установки в нём меняются три вещи: `SECRET_KEY` на собственный,
`DEBUG` на `False`, `ALLOWED_HOSTS` на реальные адреса.

При `DEBUG = False` статику раздаёт whitenoise, и её нужно предварительно
собрать:

```bash
.venv/Scripts/python.exe manage.py collectstatic
```

Сводки считаются через ORM в `views/pages.py`. Реестры, история и графики — на

`/reports/api/...` и рисуются на месте скриптом внутри шаблона.

## Таблицы

| Таблица | Что хранит |
| --- | --- |
| `staging_excel` | строки файла КДР как есть |
| `staging_znp_excel` | строки файла ЗнП (ФЗД) как есть |
| `staging_znp_sap_excel` | строки файла ЗнП (SAP) как есть |
| `igk_stat_data` | позиции договоров |
| `znp_data` | заявки на платёж (ФЗД) |
| `znp_data_sap` | заявки на платёж (SAP) |
| `contracts_history` | изменения статуса, плана, факта, суммы договора |
| `contract_counts_snapshot` | количество заключённых договоров на дату |
| `nsi_igk` | справочник ИГК, из него берётся выбор на сводках |

Таблицы `staging_*` очищаются при каждой загрузке. Рабочие таблицы не
обновляются построчно: загрузка полностью перезаписывает их, поэтому `pp_id` и
`id` меняются после каждой загрузки и не могут служить внешними ссылками.

Все адреса начинаются с `/reports/`.

| `kdr/<год>/` | КДР |

Плашки на сводках кликабельны: открывают реестр, отфильтрованный по той же
выборке, что и число на плашке. Связь держится на ключе `status_param` — он
одновременно имя условия в `views/api.py` (для ЗнП ФЗД) и в
`services/sap_status.py` (для SAP). При переименовании ключа плашка молча
откроет пустой реестр.

Селектор ИГК на сводке ЗнП влияет только на таблицу по ЦФО. Плашки сверху
считаются по всем ИГК.

## Загрузка данных

Страница `/reports/upload/` — доступна суперпользователю и группе `operator`.
Из командной строки:

```bash
python manage.py load_contracts "Выгрузка КДР.xlsx"
python manage.py load_znp "Отчет о согласованных и исполненных ЗнП.xlsx"
python manage.py load_znp_sap файл_sap.xlsx
```

Команда читает файл в `staging_*` и разбирает в рабочие таблицы. Оба шага в
одной транзакции: при ошибке база остаётся прежней.

Порядок загрузки произвольный. `load_contracts` полностью перезаписывает
`igk_stat_data` и в конце вызывает `relink_znp_parents()` — заявки ФЗД
привязываются к позициям заново по `crc32_hash`.

## Формат файлов

Строка заголовков ищется по названиям колонок, её положение в файле значения
не имеет. Если хотя бы одной колонки нет, загрузка отменяется с сообщением
«Документ не соответствует формату». Перечни колонок — в
`services/excel_import.py`.

**КДР:** ИГК, Контрагент, ЦФО, Договор, Состояние, Тип платежа, Предмет,
Заказ, ПЛАН, ФАКТ, Остаток, Тол, Этап графика, ДатаПланПодп, СУММА договора,
ГодИГК.

**ЗнП (ФЗД):** ИГК договора, ИГК заявки, Контрагент,
ДокументПланирования.Номер, Этап, Назначение платежа, Договор, Прогнозная дата
оплаты, Фактическая дата оплаты, Сумма руб планирования, Сумма руб оплаты,
ТипПлатежа, Статус, Дата.

**ЗнП (SAP):** ИГК (по договору), Отдел-исполнитель, Наименование кредитора,
Регистрационный номер, Текст, Сумма во ВВ, Наименование Банка,
ЗнП 421 отдел (ГОЗ) - (E), ЗнП 18 отдел (ГОЗ) - (F), Платеж возможен - ( ),
СП/ГП, ДокумВыравнивания.

## Как считается сводка ЗнП

«Всего ЗнП» — количество этапов оплаты у заключённых договоров, то есть строк
`igk_stat_data` со статусом из `CONCLUDED`. Допуск на этот счётчик не влияет.

«Не оформлено» — этапы без заявки, у которых остаток превышает допуск:

```text
допуск = Тол / 100 * Сумма договора
```

Пустой «Тол» и пустая «Сумма договора» считаются нулём, отрицательный допуск
приводится к нулю. Позиция попадает в «Не оформлено», только если «Остаток»
строго больше допуска. Равный, меньший, нулевой и отрицательный остаток
позицию из «Не оформлено» исключают — она остаётся в «Всего ЗнП», но не
попадает ни в одну плашку, ни в реестр, ни в график.

Поэтому плашки не обязаны складываться в «Всего ЗнП»: разница — это этапы,
которым заявка не нужна, потому что остаток укладывается в допуск.

Позиции, у которых заявка есть, правилом не затрагиваются — они идут в
«Оформлено» и «На оформлении». Проценты на плашках считаются от «Всего ЗнП».

Условие задано один раз в `queries.needs_znp()` и используется тремя местами:
плашками в `views/pages.py`, реестром в `views/api.py`, графиком в
`services/charts.py`.

## Связь заявок с договорами

Заявка ФЗД привязывается к позиции договора по `crc32_hash` от четырёх полей:
ИГК, контрагент, договор, этап графика. Если хотя бы одно поле в двух
выгрузках записано по-разному, привязки не будет и заявка не попадёт ни на
одну страницу — все выборки идут через `parent`.

Полей связки в `znp_data` нет, они остаются в `staging_znp_excel` до следующей
загрузки ЗнП. Непривязанные заявки:

```sql
SELECT s.igk, s.c_agent, s.contract, s.stage, count(*) AS cnt
FROM znp_data z
JOIN staging_znp_excel s ON s.crc32_hash = z.crc32_hash
WHERE z.parent_id IS NULL
GROUP BY 1, 2, 3, 4 ORDER BY cnt DESC LIMIT 15;
```

В каком поле расхождение — по числу совпадений при сужении ключа:

```sql
SELECT
  count(*) FILTER (WHERE EXISTS (SELECT 1 FROM igk_stat_data i
    WHERE i.igk = s.igk AND i.c_agent = s.c_agent
      AND i.contract = s.contract AND TRIM(i.stage) = TRIM(s.stage))) AS все_четыре,
  count(*) FILTER (WHERE EXISTS (SELECT 1 FROM igk_stat_data i
    WHERE i.igk = s.igk AND i.c_agent = s.c_agent
      AND i.contract = s.contract)) AS без_этапа,
  count(*) FILTER (WHERE EXISTS (SELECT 1 FROM igk_stat_data i
    WHERE i.igk = s.igk AND i.c_agent = s.c_agent)) AS игк_и_контрагент,
  count(*) FILTER (WHERE EXISTS (SELECT 1 FROM igk_stat_data i
    WHERE i.igk = s.igk)) AS только_игк,
  count(*) AS всего
FROM staging_znp_excel s;
```

Скачок между соседними столбцами указывает на расходящееся поле.

## Права доступа

| Роль | Права |
| --- | --- |
| суперпользователь | все страницы, включая сводки и загрузку |
| группа `operator` | загрузка файлов |
| прочие | страницы и выгрузки |

Группа создаётся командой `python manage.py setup_groups`.

## Общие константы

`services/queries.py` — единственное место, где заданы значения, влияющие на
все отчёты:

| Константа | Назначение |
| --- | --- |
| `CONCLUDED`, `NOT_CONCL`, `TERMINATED` | статусы договора |
| `ADVANCE`, `POSTPAYMENT` | типы платежа |
| `ZNP_APPROVED` | статус утверждённой заявки |
| `YEARS`, `YEAR_COL` | годы и колонки-флаги |
| `HAS_ORDER` | условие наличия заказа у строки |
| `needs_znp()` | условие «остаток превышает допуск» |
| `valid_year()` | приведение года из URL или параметра к допустимому |
| `SAP_CFO` | отделы МТО (420–429) |

Часть правил существует в двух видах — для сырого SQL и для ORM. При изменении
править оба:

| Правило | SQL | ORM |
| --- | --- | --- |
| «есть заказ» | `HAS_ORDER` в `queries.py` | `HAS_ORDER_Q` в `views/pages.py` |
| «остаток превышает допуск» | `needs_znp()` | она же через `RawSQL` в `znp_table` |
| статус ЗнП (ФЗД) | `ZNP_STATUS_CONDITIONS` в `views/api.py` | `znp_aggregates()` в `services/dashboards.py` |

Статус заявки SAP сведён в один модуль `services/sap_status.py`: там и метки,
и условия фильтрации, и выражение для ORM, и текст `CASE` для сырого SQL.

Статусы, не перечисленные в `CONCLUDED`, `NOT_CONCL` и `TERMINATED`, попадают
в «Всего договоров», но не попадают ни в одну из трёх групп.

## Как добавить новый год

На примере 2028:

1. `services/queries.py` — `YEARS = [2025, 2026, 2027, 2028]`
2. `models.py` — поле `y28 = models.BooleanField(null=True)` в `IgkStatData`
3. `services/normalize.py` — `y28` в распаковку `year_flags()`, в кортеж
   `new_data.append(...)` и в перечень колонок INSERT
4. `python manage.py makemigrations` и `python manage.py migrate`

Год берётся из колонки «ГодИГК» файла КДР: первые четыре символа значения
сравниваются с элементами `YEARS`.
