# supply_service — веб-сервис отчётных форм для отдела снабжения

Django-приложение, которое загружает выгрузки из учётных систем (договоры, заявки на платёж ФЗД и SAP, отчёты ЕИС ГОЗ), хранит их в PostgreSQL и показывает сводки, реестры и графики, а также формирует отчёты в Excel.

## Архитектура

```
Браузер (HTML + JavaScript)
         ↕  HTTP / AJAX
    Django (Python) — логика
         ↕  SQL / ORM
    PostgreSQL — хранение данных
```

- Страницы отдают только каркас, таблицы подгружаются JavaScript-ом из JSON API (`/reports/api/...`) без перезагрузки.
- Сложные аналитические запросы (агрегации с FILTER, NULLIF) написаны сырым SQL в `services/queries.py` и `services/charts.py`. ORM используется для схемы, миграций и сводок SAP.
- Загрузка идёт в два шага: файл читается в staging-таблицу «как есть», затем нормализуется в рабочую таблицу. Оба шага выполняются в одной транзакции, при ошибке всё откатывается.

## Заявки на платёж SAP

Сводка `znp-sap/` показывает три блока карточек: «Все заявки», «Заявки за <выбранная дата>» и «Заявки за предыдущий рабочий день». Под ними таблица по ЦФО (420–429) для выбранного ИГК и график.

### Карточки

Карточки считаются независимо друг от друга, одна заявка может попасть в несколько. Условия заданы в одном месте — `reports/services/sap_status.py`, функция `sap_status_conditions()`.

| Карточка                        | Условие                                  |
| ------------------------------- | ---------------------------------------- |
| Всего ЗнП (SAP)                 | число всех заявок (`Count`)              |
| На согласовании                 | `stage_e` и `stage_f` пусты              |
| Согласовано для передачи в реестр | `stage_c` не пуст                      |
| Передано в 18 отдел             | `stage_e` не пуст                        |
| Подтверждено 18 отделом         | `stage_f` не пуст, номера документа нет  |
| Оплачено                        | номер документа (`normalize_doc_num`) есть |
| Готово к передаче в 18 отдел    | `stage_e` в будущем                      |

Колонка «Этап» в реестре и стек графика показывают один статус на заявку (`sap_status_expr()` и `sap_status_sql()`), поэтому их числа могут отличаться от карточек.

### Выбранная дата

Дата на сводке жёсткая, и в карточках, и в списке по клику:

- для «Согласовано для передачи в реестр» сравнивается `stage_c`;
- для всех остальных статусов сравнивается `stage_e` (дата передачи в 18 отдел);
- «Всего» в блоке даты — заявки с `stage_e`, равной этой дате.

Из-за этого «На согласовании» в блоках дат всегда 0: у такой заявки `stage_e` пуст. Процент для «Согласовано для передачи в реестр» показывается только в блоке «Все заявки»: в блоках дат он считался бы по другому полю даты и не имел бы смысла.

Вторая дата — предыдущий рабочий день: для понедельника это пятница (−3 дня), для воскресенья пятница (−2 дня), для остальных дней −1 день. Праздники не учитываются.

### Как не разойтись числам на карточке и в списке

Карточки (`services/dashboards.py`, `sap_aggregates`) и список (`views/api.py`, `api_znp_sap_list`) берут условия из одной функции `sap_status_conditions()`, а поле даты — из `sap_date_field()`. При изменении карточек править нужно только `sap_status.py`.

### Колонки файла SAP

Формат файла стабилен, поэтому колонки берутся по фиксированным индексам (нумерация с 0), строка заголовка пропускается. Загружаются только строки с типом `ГОЗ`.

| Поле                  | Индекс |
| --------------------- | ------ |
| Тип                   | 8      |
| Номер документа       | 10     |
| Текст (предметы)      | 11     |
| Сумма во ВВ           | 12     |
| Контрагент            | 14     |
| Рег. номер            | 18     |
| ИГК                   | 19     |
| ЦФО                   | 22     |
| Банк                  | 24     |
| Этап C                | 27     |
| Этап E                | 29     |
| Этап F                | 30     |
| Возможная дата оплаты | 31     |

Заявки SAP перезаписываются целиком при каждой загрузке (без истории). В реестре «Дата оплаты» показывается только для оплаченных заявок.

## Загрузка данных

### Через веб-интерфейс

1. Открыть **Загрузка данных** (нужно право «Загрузка данных»).
2. Выбрать файл `.xlsx` или `.xls`.
3. Выбрать тип файла: «Договоры», «ЗНП (ФЗД)» или «ЗНП (SAP)».
4. Нажать **Загрузить и нормализовать**.

### Через командную строку

```
python manage.py load_contracts путь\к\файлу.xlsx
python manage.py load_znp путь\к\файлу.xlsx
python manage.py load_znp_sap путь\к\файлу.xlsx
```

Каждая команда сама импортирует файл в staging и нормализует данные в одной транзакции. После загрузки время записывается в `system_events` и показывается на сводках как «Актуально на …».

### Форматы файлов

- **Договоры** и **ЗНП (ФЗД)** — шапкой считается первая строка с известными заголовками, порядок колонок не важен. Нужные заголовки заданы в `CONTRACT_COLUMNS` и `ZNP_COLUMNS` в `services/excel_import.py`. Если нужной колонки нет, загрузка прерывается с ошибкой «Документ не соответствует формату».
- **ЗНП (SAP)** — по индексам колонок, см. таблицу выше.

**Договоры.** Год позиции определяется по колонке `ГодИГК` (4-значный год из списка `YEARS`). Типы платежей: `Аванс`, `Постоплата`. Статусы:

- заключённые: `Исполняется`, `Возвращен на уточнение`, `На согласовании`, `Подписан`, `На утверждении`;
- незаключённые: `Черновик`;
- расторгнутые: `Расторгнут`.

При повторной загрузке договоры сравниваются с предыдущей версией: изменения статуса, плана и факта попадают в `contracts_history`, появившиеся договоры — в `contracts_appeared`.

**Заявки ФЗД** привязываются к позициям договоров по `crc32_hash` (ИГК, контрагент, договор, этап). Заявки без совпадения на страницах не показываются.

## Анализ ГОЗ и справочник ГК

Страница `goz-report/` принимает ZIP-архив с отчётами ЕИС ГОЗ (файлы `.xls`), сопоставляет контракты со справочником ставок НДС и отдаёт готовый Excel «Анализ ГОЗ». Разбор архива — `services/goz_analysis.py`.

- Один `.xls` — один контракт, ГК определяется по имени файла.
- Ставка НДС берётся из справочника ГК (таблица `goz_contract_vat`: ГК, год, изделие, ставка НДС). На странице справочник можно добавлять, изменять и удалять.
- Загрузка справочника из Word или Excel-файла доступна только суперпользователям.

## Права доступа

Каждый раздел закрыт отдельным правом (модель-заглушка `Access`, таблица не создаётся). Проверка выполняется в `reports/middleware.py`: раздел определяется по имени маршрута, при отсутствии права возвращается страница 403 (для API — JSON).

| Право               | Раздел            |
| ------------------- | ----------------- |
| `access_dashboard`  | Договорная работа |
| `access_znp`        | ЗнП (ФЗД)         |
| `access_znp_sap`    | ЗнП (SAP)         |
| `access_kdr`        | КДР по годам      |
| `access_igk`        | ИГК по годам      |
| `access_history`    | История изменений |
| `access_dupes`      | Дубликаты         |
| `access_export`     | Отчёты в Excel    |
| `access_upload`     | Загрузка данных   |
| `access_goz_report` | Анализ ГОЗ        |

Права назначаются в админке `/admin/`: Пользователи → выбрать пользователя → права доступа. Суперпользователь имеет все права. При создании пользователя автоматически создаётся профиль, данные сотрудника можно подтянуть из HR-сервиса (адрес задаётся переменной `HR_SERVICE_API_URL`).

Создание суперпользователя:

```
python manage.py createsuperuser
```

## Развёртывание

### Требования

- Python 3.12+
- PostgreSQL 16+ (расширение `pgcrypto` создаётся миграцией)

### Установка

```
cd supply_service
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

### Переменные окружения

Создать `.env` в корне проекта:

```
DJANGO_SECRET_KEY=любая-длинная-случайная-строка-минимум-50-символов
DJANGO_DEBUG=True
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1
DB_NAME=supply_service
DB_USER=postgres
DB_PASSWORD=пароль_от_postgresql
DB_HOST=localhost
DB_PORT=5432
HR_SERVICE_API_URL=
```

`HR_SERVICE_API_URL` нужен только для синхронизации сотрудников с HR-системой, без него остальное работает.

### Запуск

```
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

Открыть: <http://127.0.0.1:8000> (перенаправит на `/reports/`).

### Продакшн

При `DJANGO_DEBUG=False` статика отдаётся через WhiteNoise, перед запуском её нужно собрать:

```
python manage.py collectstatic
```

## Добавление нового года

Например, 2028. Годовые флаги хранятся отдельными колонками (`y25`, `y26`, `y27`), поэтому менять нужно несколько мест:

1. **`reports/services/queries.py`** — добавить год в `YEARS`:

   ```python
   YEARS = [2025, 2026, 2027, 2028]
   ```

   `YEAR_COL` и `YEAR_MAP` в `normalize.py` строятся из `YEARS` автоматически.

2. **`reports/models.py`** — добавить поле в `IgkStatData`:

   ```python
   y28 = models.BooleanField(null=True, verbose_name="Флаг 2028 года")
   ```

3. **`reports/services/normalize.py`** — в `normalize_contracts` добавить `y28` в распаковку `year_flags(...)`, в кортеж данных, в список колонок и в число `%s` в INSERT.

4. **`reports/services/queries.py`** — добавить `y28` в SQL `all_contracts` (списки колонок в SELECT и GROUP BY).

5. **`reports/admin.py`** — при желании добавить `y28` в `list_display` и `list_filter`.

6. Создать и применить миграцию:

   ```
   python manage.py makemigrations reports
   python manage.py migrate
   ```

7. Заново загрузить файл договоров.
