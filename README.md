# supply_service

Сервис учёта договоров и заявок на платёж. Принимает выгрузки Excel, хранит их
в PostgreSQL, показывает сводки и реестры, формирует выгрузки Excel.

## Стек

Django 6, PostgreSQL, openpyxl, whitenoise. Фронтенд без сборки: Bootstrap и
Chart.js лежат файлами в `reports/static/vendor/`.

Нужны Python 3.13 и PostgreSQL. Колёса `psycopg2_binary` в `wheels/` собраны
под `cp313` и на другую версию Python не встанут.

## Развёртывание

### База

Роль и база создаются один раз от имени `postgres`:

```sql
CREATE ROLE <пользователь> LOGIN SUPERUSER PASSWORD '<пароль>';
CREATE DATABASE <база> OWNER <пользователь>;
```

Роль заводится суперпользователем: миграция `0014_pgcrypto` создаёт расширение
`pgcrypto`, на его функции `digest()` построены SQL истории изменений и поиска
дубликатов. Для прогона тестов роли нужно право `CREATEDB` — тесты поднимают
отдельную базу.

Те же значения прописываются в `DATABASES` в `supply_service/settings.py`.

### Приложение

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe manage.py migrate
.venv/Scripts/python.exe manage.py createsuperuser
.venv/Scripts/python.exe manage.py runserver
```

### Установка без интернета

В `wheels/` лежат пакеты для офлайн-установки:

```bash
.venv/Scripts/python.exe -m pip install --no-index --find-links wheels -r requirements.txt
```

Готовую папку `.venv` переносить с другой машины нельзя — в ней записан
абсолютный путь к Python. Её создают заново на месте.

### Перенос данных

Данные переносятся дампом:

```bash
pg_dump -U <пользователь> -d <база> -F c -f supply_service.dump
pg_restore -U <пользователь> -d <база> supply_service.dump
```

Повторная загрузка исходных файлов Excel восстанавливает договоры и заявки, но
не историю: `contracts_history` и `contract_counts_snapshot` накапливаются от
загрузки к загрузке.

## Настройки

`supply_service/settings.py` — единственный файл настроек. Он лежит в
репозитории и правится под машину. При переносе на сервер меняются четыре
вещи:

| Настройка | Значение на сервере |
| --- | --- |
| `SECRET_KEY` | собственный, не из репозитория |
| `DEBUG` | `False` |
| `ALLOWED_HOSTS` | адреса сервера |
| `DATABASES` | имя базы, пользователь, пароль, хост |

При `DEBUG = False` статику раздаёт whitenoise со сжатием и хешами в именах
файлов, поэтому её нужно предварительно собрать:

```bash
.venv/Scripts/python.exe manage.py collectstatic
```

При `DEBUG = True` работает обычное хранилище статики, собирать ничего не
нужно.

Ответы сжимаются `GZipMiddleware`: реестры отдают десятки тысяч строк, и без
сжатия это мегабайты на запрос.

## Структура

```text
reports/
├── models.py                 схема базы
├── urls.py                   маршруты
├── middleware.py             проверка прав на разделы
├── admin.py
│
├── views/
│   ├── pages.py              страницы: сводки, реестры, загрузка
│   ├── api.py                JSON для таблиц и графиков
│   └── exports.py            выгрузки Excel
│
├── services/
│   ├── excel_import.py       чтение xlsx в staging_*, перечни колонок файлов
│   ├── normalize.py          перенос staging_* в рабочие таблицы, история изменений
│   ├── linking.py            crc32-хеш и привязка заявок к позициям договоров
│   ├── queries.py            SQL реестров и отчётов, общие константы
│   ├── charts.py             SQL графиков по ЦФО
│   ├── dashboards.py         расчёт плашек и строк по ЦФО
│   ├── sap_status.py         статус заявки SAP по датам этапов
│   ├── excel.py              сборка книги xlsx
│   └── pivot.py              выгрузка авансов по шаблону
│
├── management/commands/
│   ├── load_contracts.py     загрузка договоров
│   ├── load_znp.py           загрузка заявок ФЗД
│   └── load_znp_sap.py       загрузка заявок SAP
│
├── tests/                    тесты загрузки, доступов и выгрузок
├── templates/                страницы
└── static/                   стили, скрипты, Bootstrap и Chart.js
```

Сводки считаются через ORM в `views/pages.py`. Реестры, история и графики — на
сыром SQL: страница отдаёт только каркас, данные подгружаются запросом к
`/reports/api/...` и рисуются на месте скриптом внутри шаблона.

## Таблицы

| Таблица | Что хранит |
| --- | --- |
| `staging_excel` | строки файла договоров как есть |
| `staging_znp_excel` | строки файла заявок ФЗД как есть |
| `staging_znp_sap_excel` | строки файла заявок SAP как есть |
| `igk_stat_data` | позиции договоров |
| `znp_data` | заявки на платёж (ФЗД) |
| `znp_data_sap` | заявки на платёж (SAP) |
| `contracts_history` | изменения статуса, плана, факта, суммы договора |
| `contract_counts_snapshot` | количество заключённых договоров на дату |
| `nsi_igk` | справочник ИГК, из него берётся выбор на сводках |

Таблицы `staging_*` очищаются при каждой загрузке. Рабочие таблицы не
обновляются построчно: загрузка полностью перезаписывает их, поэтому `pp_id` и
`id` меняются после каждой загрузки и не могут служить внешними ссылками.

Заявка ФЗД привязывается к позиции договора по `crc32_hash` от четырёх полей:
ИГК, контрагент, договор, этап графика. Если хотя бы одно поле в двух
выгрузках записано по-разному, привязки не будет и заявка не попадёт ни на
одну страницу — все выборки идут через `parent`.

## Страницы

Все адреса начинаются с `/reports/`.

| Адрес | Что показывает |
| --- | --- |
| `dashboard/` | сводка по договорам: плашки и таблица по ЦФО |
| `znp/` | сводка заявок ФЗД, график с выбором периода по дате заявки |
| `znp-sap/` | сводка заявок SAP |
| `all-contracts/` | реестр договоров |
| `znp-list/` | реестр заявок ФЗД |
| `znp-sap-list/` | реестр заявок SAP |
| `kdr/<год>/` | контроль договорной работы |
| `igk-concluded/<год>/` | заключённые по ИГК |
| `igk-not-concluded/<год>/` | незаключённые по ИГК |
| `igk-terminated/<год>/` | расторгнутые по ИГК |
| `history-status/` | история изменений статуса |
| `history-plan/` | история изменений плана |
| `history-fact/` | история изменений факта |
| `contract-dupes/` | дубликаты договоров |
| `upload/` | загрузка файлов |
| `export/` | выгрузки Excel |

Плашки на сводках кликабельны: открывают реестр, отфильтрованный по той же
выборке, что и число на плашке. Связь держится на ключе `status_param` — он
одновременно имя условия в `views/api.py` (для заявок ФЗД) и в
`services/sap_status.py` (для SAP). При переименовании ключа плашка молча
откроет пустой реестр.

Селектор ИГК на сводках влияет только на таблицу по ЦФО. Плашки сверху
считаются по всем ИГК.

## Загрузка данных

Страница `/reports/upload/` доступна тем, у кого есть право `access_upload`.
Из командной строки:

```bash
.venv/Scripts/python.exe manage.py load_contracts <файл.xlsx>
.venv/Scripts/python.exe manage.py load_znp <файл.xlsx>
.venv/Scripts/python.exe manage.py load_znp_sap <файл.xlsx>
```

Команда читает файл в `staging_*` и разбирает в рабочие таблицы. Оба шага в
одной транзакции: при ошибке база остаётся прежней.

Порядок загрузки произвольный. `load_contracts` полностью перезаписывает
`igk_stat_data` и в конце вызывает `relink_znp_parents()` — заявки ФЗД
привязываются к позициям заново по `crc32_hash`.

## Формат файлов

Строка заголовков ищется по названиям колонок, её положение в файле значения
не имеет. Если хотя бы одной колонки нет, загрузка отменяется с сообщением
«Документ не соответствует формату».

Перечни колонок заданы в `services/excel_import.py` — по одному словарю на
каждый тип файла: `CONTRACT_COLUMNS`, `ZNP_COLUMNS`, `ZNP_SAP_COLUMNS`. Ключ
словаря — заголовок в файле, значение — поле таблицы `staging_*`. Других мест,
где перечислены колонки исходных файлов, в проекте нет.

## Права доступа

Доступ выдаётся по разделам, галочками на странице пользователя в админке —
без правки кода. Под капотом это девять обычных Permission Django,
объявленных на модели `Access` (таблицы у неё нет, `managed = False`).

| Право | Что открывает |
| --- | --- |
| `access_dashboard` | сводка по договорам, реестр договоров, графики |
| `access_znp` | заявки ФЗД: сводка и реестр |
| `access_znp_sap` | заявки SAP: сводка и реестр |
| `access_kdr` | контроль договорной работы по годам |
| `access_igk` | ИГК по годам, все три вида |
| `access_history` | история изменений |
| `access_dupes` | дубликаты |
| `access_export` | выгрузки Excel |
| `access_upload` | загрузка данных |

Проверку делает `reports/middleware.py`: он смотрит имя маршрута и ищет в нём
ключевое слово раздела. Порядок в `SECTIONS` значим — `export` проверяется
раньше `kdr`, чтобы `export_kdr` считался выгрузкой, а `znp_sap` раньше `znp`.
Проверка стоит на страницах, на API и на выгрузках. Суперпользователь проходит
везде. Главная страница, вход и выход открыты всем, кто вошёл. Меню и карточки
на главной прячут разделы, к которым прав нет.

## Общие константы

`services/queries.py` — единственное место, где заданы значения, влияющие на
все отчёты:

| Константа | Назначение |
| --- | --- |
| `CONCLUDED`, `NOT_CONCL`, `TERMINATED` | статусы договора |
| `ADVANCE`, `POSTPAYMENT` | типы платежа |
| `ZNP_APPROVED` | статус утверждённой заявки |
| `YEARS`, `YEAR_COL` | годы и колонки-флаги |
| `HAS_ORDER` | условие наличия заказа у строки |
| `needs_znp()` | условие «остаток превышает допуск» |
| `valid_year()`, `valid_date()` | приведение года и даты из параметров запроса |
| `SAP_CFO` | перечень ЦФО, попадающих в сводку SAP |

Статусы, не перечисленные в `CONCLUDED`, `NOT_CONCL` и `TERMINATED`, попадают
в общее количество договоров, но не попадают ни в одну из трёх групп.

Часть правил существует в двух видах — для сырого SQL и для ORM. При изменении
править оба:

| Правило | SQL | ORM |
| --- | --- | --- |
| «есть заказ» | `HAS_ORDER` в `queries.py` | `HAS_ORDER_Q` в `views/pages.py` |
| «остаток превышает допуск» | `needs_znp()` | она же через `RawSQL` в `znp_table` |
| статус заявки ФЗД | `ZNP_STATUS_CONDITIONS` в `views/api.py` | `znp_aggregates()` в `services/dashboards.py` |

Статус заявки SAP сведён в один модуль `services/sap_status.py`: там и метки,
и условия фильтрации, и выражение для ORM, и текст `CASE` для сырого SQL.

## Как добавить новый год

На примере 2028:

1. `services/queries.py` — `YEARS = [2025, 2026, 2027, 2028]`
2. `models.py` — поле `y28 = models.BooleanField(null=True)` в `IgkStatData`
3. `services/normalize.py` — `y28` в распаковку `year_flags()`, в кортеж
   `new_data.append(...)` и в перечень колонок INSERT
4. `manage.py makemigrations` и `manage.py migrate`

Год берётся из колонки «ГодИГК» файла договоров: первые четыре символа
значения сравниваются с элементами `YEARS`.
