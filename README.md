# supply_service

Django-сервис отчётности отдела снабжения: договоры, заявки на платёж и выгрузки
в Excel. Данные приходят выгрузками из внешних систем, загружаются через веб или
командой, дальше показываются на дашбордах и в реестрах.

Реестры устроены одинаково: страница отдаёт разметку, JS забирает JSON из
`views/api.py` и рисует таблицу без перезагрузки. Дашборды считаются на сервере
через ORM. Тяжёлые агрегаты (FILTER, группировки по статусам и годам) написаны
сырым SQL и вынесены в `services/queries.py`.

## Страницы

| Адрес | Что показывает | Кому |
|---|---|---|
| `/reports/` | обзор | всем |
| `/reports/dashboard/` | договорная работа: карточки, разрез по ЦФО, давность незаключённых | superuser |
| `/reports/znp/` | заявки на платёж (ФЗД): этапы оформления и оплаты | superuser |
| `/reports/znp-sap/` | заявки на платёж (SAP): этапы согласования | superuser |
| `/reports/kdr/<год>/` | статистика заключения договоров | всем |
| `/reports/igk-concluded/<год>/` и рядом | ИГК по статусам | всем |
| `/reports/all-contracts/` | реестр договоров | всем |
| `/reports/znp-list/` | реестр ЗнП (ФЗД) | всем |
| `/reports/znp-sap-list/` | реестр ЗнП (SAP) | всем |
| `/reports/history-*/` | история изменений статуса, плана, факта | всем |
| `/reports/contract-dupes/` | дубликаты позиций: полные повторы и один заказ в разных договорах | всем |
| `/reports/export/` | отчёты в Excel | всем |
| `/reports/upload/` | загрузка файлов | operator, superuser |

Внизу каждого дашборда, под таблицей по ЦФО, график:

- договорная работа — незаключённые по ЦФО, сегменты по давности срока;
- ЗнП (ФЗД) — заявки по ЦФО, сегменты по стадиям;
- ЗнП (SAP) — заявки по ЦФО, сегменты по этапам согласования.

ЦФО отсортированы по сумме: где столбец длиннее, там узкое место. Числа те же,
что в таблице выше, — график добавляет к ней сравнение между ЦФО.

Цвет карточек и полос читается как движение по этапам: красный (стоит) →
оранжевый → янтарный → синий (почти) → зелёный (готово).

Меню собрано по назначению: сначала «Сводки» (дашборды), сразу за ними
«Реестры» — все договоры и оба реестра ЗнП, дальше КДР, ИГК, история и
служебные страницы.

В обоих реестрах фильтры одинаковые: поиск, ИГК, ЦФО, год, статус. Поиск —
одно поле на контрагента и номер договора, по части строки, без подсказок.

Роли задаются в `/admin/`: Пользователи → выбрать → Группы. Группы `viewer` и
`operator` создаёт `python manage.py setup_groups`. Разница: `operator` может
загружать файлы. Дашборды доступны только суперпользователю, остальным
показывается страница об отсутствии прав.

## Таблицы базы

| Таблица | Что хранит |
|---|---|
| `igk_stat_data` | позиции договоров: одна строка = один этап и один тип платежа |
| `znp_data` | заявки на платёж (ФЗД), привязаны к позиции договора |
| `znp_data_sap` | заявки на платёж (SAP), самостоятельные записи без привязки |
| `staging_*` | сырые строки Excel до нормализации |
| `contracts_history` | изменения статуса, плана и факта между загрузками |
| `contract_counts_snapshot` | снимки числа заключённых договоров для дельты в КДР |
| `nsi_igk`, `nsi_cfo` | справочники, заполняются сами при загрузке |

### Связь ЗнП с договорами

`znp_data.parent_id` ссылается на `igk_stat_data.pp_id`, но **без ограничения
внешнего ключа**. Причина: при каждой загрузке договоров `igk_stat_data`
очищается и заполняется заново, а номера `pp_id` выдаются с нуля. Обычный внешний
ключ снёс бы все заявки каскадом.

Связь восстанавливается по `crc32_hash` — хешу от ИГК, контрагента, договора и
этапа. Этим занимается `services/znp_linking.py::relink_znp_parents()`, его
вызывает `normalize_staging.py` последним шагом. Без этого вызова заявки остаются
с номерами от прошлой раскладки и молча оказываются привязаны к чужим договорам.

Поле `is_deleted` в `igk_stat_data` не заполняется: источник присылает полные
дубли строк без уникального идентификатора, отследить удаление нечем.

## Миграции

Четыре: `0001_initial` создаёт все таблицы,
`0002_performance_indexes_and_snapshot_key` — индексы и уникальный ключ снимков,
`0003_sap_indexes` — индексы по ЦФО и ИГК для заявок SAP,
`0004_znp_status` — поле статуса заявки ЗнП.

На базах, где раньше применялась старая цепочка, в журнале могли остаться записи
о миграциях, файлов которых больше нет. Django их игнорирует, но
`showmigrations` из-за них показывает лишнее. Чистится один раз:

```sql
DELETE FROM django_migrations WHERE app = 'reports' AND name <> '0001_initial';
```

## Загрузка данных

Через интерфейс: «Загрузка данных» → выбрать файл и тип → загрузить.

Через командную строку:

```bash
python manage.py load_contracts файл.xlsx
python manage.py load_znp файл.xlsx
python manage.py load_znp_sap файл.xlsx
```

Каждая команда делает два шага одной транзакцией: кладёт сырые строки в
`staging_*`, затем разбирает их и переносит в рабочие таблицы. Если второй шаг
упадёт, первый откатится и данные останутся прежними.

Повторная загрузка договоров сравнивается с предыдущей: изменения статуса, плана
и факта попадают в «Историю изменений». По ЗНП истории нет, хранится только
текущий снимок.

Типы файлов перечислены двумя словарями в начале `views/pages.py`. Новый тип —
пара «ключ-значение» в оба словаря, шаблон и представление менять не нужно.

## Формат файлов Excel

### Договоры

Заголовки в первой строке, порядок колонок не важен:

Колонки обязательны все до одной: если хоть одной нет, загрузка прерывается
и данные не меняются.

```text
ИГК | Контрагент | ЦФО | Договор | Состояние | Тип платежа | Предмет | Заказ |
ПЛАН | ФАКТ | Тол | Этап графика | ДатаПланПодп | ГодИГК
```

- **ГодИГК** — четырёхзначный год.
- **ДатаПланПодп** — дата вида `ДД.ММ.ГГГГ`, при нормализации приводится
  к `ГГГГ.ММ`; по ней строится график по месяцам.
- **Тип платежа** — `Аванс` или `Постоплата`, прочее в авансовых расчётах не
  участвует.
- **Состояние**: заключённые — `Исполняется`, `Возвращен на уточнение`,
  `На согласовании`, `Подписан`, `На утверждении`, `Исполнен`; незаключённые —
  `Черновик`; расторгнутые — `Расторгнут`.

Без колонок ИГК, Контрагент, Договор и Этап графика загрузка прерывается: из них
считается хеш связки с ЗНП, и без него связь порвётся у всех заявок сразу.

### ЗнП (ФЗД)

Заголовок в первой строке:

```text
ИГК договора | ИГК заявки | Контрагент | ДокументПланирования.Номер | Этап |
Назначение платежа | Договор | Прогнозная дата оплаты | Фактическая дата оплаты |
ТипПлатежа | Статус | Сумма руб планирования | Сумма руб оплаты
```

- **Статус** — `Утвержден` или `На утверждении`. Заявки со статусом
  «На утверждении» попадают на карточку «На оформлении», «Утвержден» —
  в «Оформлено» и дальше делятся по типу платежа.

- **ИГК договора** — ИГК позиции, к которой привязана заявка. **ИГК заявки** —
  ИГК, по которому заявка фактически оплачена, может отличаться. В реестре обе
  колонки показаны отдельно.
- **Этап** — это «Этап графика платежей» из файла договоров, а не статус заявки.
  Значение должно совпадать с файлом договоров, иначе хеш не сойдётся и заявка
  останется без привязки.

## Заявки на платёж: как считаются

Два независимых источника: **ФЗД** и **SAP**. Заявки SAP не связаны с
`igk_stat_data` — это самостоятельные записи, и статус у них считается по этапу
согласования.

### ФЗД

Считаются позиции заключённых договоров, а не строки `znp_data` напрямую:

- у позиции нет ни одной заявки → «Не оформлено ЗнП», счётчик считает **позиции**;
- заявка со статусом «На утверждении» → «На оформлении ЗнП»;
- заявка со статусом «Утвержден» → «Оформлено ЗнП», дальше по типу платежа позиции.
  Счётчик считает **заявки**: если у одной позиции их несколько, каждая идёт
  отдельно;
- из оформленных отдельно считается «Оплачено» — заявки с заполненной фактической
  суммой.

Суммы: «не оформлено» — плановая сумма позиции, других данных нет; «оформлено» —
плановая сумма заявок; «оплачено» — фактическая сумма заявок.

Проценты на карточках: «оформлено» — доля от общего числа, «оплачено» — доля от
«оформлено» той же группы, а не от общего числа.

Условия статуса продублированы в двух местах: `ZNP_STATUS_CONDITIONS` в
`views/api.py` (фильтр реестра) и `CASE` в `queries.py::znp_list()`
(отображаемый статус). Меняя логику, править нужно оба.

### SAP

Четыре этапа по датам согласования: на согласовании → передано в 18 отдел →
подтверждено 18 отделом → оплачено. Логика живёт в `services/sap_status.py` в
одном экземпляре: выражение для ORM и функция для построчной подписи в JSON
обязаны оставаться согласованными.

## Добавление нового года

Например, 2028. Четыре места:

**1. `services/queries.py`**

```python
YEARS = [2025, 2026, 2027, 2028]
```

**2. `models.py`** — новое поле в `IgkStatData`:

```python
y28 = models.BooleanField(null=True)
```

**3. `management/commands/normalize_staging.py`** — добавить `y28` в распаковку
`year_flags()`, в кортеж `new_data.append(...)` и в список колонок INSERT.

**4. Миграция:**

```bash
python manage.py makemigrations reports
python manage.py migrate
```

После этого перезагрузить файл договоров. Дашборды ЗНП править не нужно — год
они берут с самой позиции договора.
